# [Lessons Learned] 架構轉型：Discord Bot → API Server 的關鍵決策
- **日期：** 2026-05-25
- **作者：** Lucas
- **相關任務：** T13（迭代維護）

## 發生什麼事
Lucas Discord Bot 和八雲 Discord Bot 存在三個重大穩定性問題：
1. 長文截斷導致 >2000 chars 的回覆崩潰丟失
2. `execFileSync` 阻塞 Event Loop 長達 30 秒
3. 同步檔案 I/O 在高併發時競爭寫入

## 根本原因
- 最初架構設計時以「快速打通」為優先，沒有考慮企業級穩定性
- Discord.js 的通訊層 + 任務處理層 + Agent 路由層全部混在同一支程式
- SSE 串流（打字機效果）增加了不必要的複雜度

## 改善措施
1. 徹底分離：Discord 通訊層交給 n8n，Lucas 轉型為純後端 API Worker
2. 建立 `lucas_api.js` v3.0：單一 POST /api/execute 端點，回傳 JSON
3. 非同步橋接層 `agent_runner.js`：execFile + Promise，零阻塞
4. 5 項測試全面通過（health / LLM / Agent / history / 400）

## 如何避免再犯
- 任何新模組的「通訊層」與「業務邏輯層」必須分離
- 使用 child_process 時永遠用 execFile（非同步），不用 execFileSync
- 長文字回覆（>2000 chars）的處理是通訊層的責任，API 只傳原始 data
